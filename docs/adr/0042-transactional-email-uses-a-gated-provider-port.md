# Transactional email uses a gated provider port

Beagle Classroom will send transactional email through a single provider-agnostic port rather than calling an email service directly from feature code. The port accepts a typed message — a recipient, a named template, and its parameters — never raw HTML assembled at the call site, so every message is auditable and every provider is swappable behind one seam.

Email is required by three flows that are otherwise blocked: a verified-email change confirms the new address through a single-use link, fallback-password recovery sends a single-use link, and Teacher Invite delivery can move from a manually copied link to an automatic send. Each link is a signed, audience-scoped, short-lived token in the pattern already used for pending onboarding and account recovery — jose HS256, a dedicated audience, a fifteen-minute expiry, single use — so the email carries proof the server can re-verify and nothing the browser is trusted to supply. Recovery and verification sends are rate-limited per address through the existing limiter so the endpoints cannot be used to mailbomb a person.

The default provider is Resend, chosen for a plain HTTP API that suits the Vercel serverless runtime where a long-lived SMTP connection is a liability. Amazon SES is the documented alternative for lower per-message cost at the price of IAM and domain-verification setup, and Postmark is a near-equivalent to Resend; raw SMTP is rejected as serverless-hostile. Because the port hides the provider, this choice is reversible without touching feature code.

The port lives in a new `lib/email/` module and ships with three adapters: the Resend adapter for production, a log-only adapter that records that a send was requested but transmits nothing for local and QA runs, and a captured-outbox adapter for integration tests that asserts the recipient and template parameters. Every email flow is therefore verifiable on the isolated QA branch exactly like the token flows, with no real message sent and no external key required.

Delivery is fail-closed and additive. The provider is active only when both the identity feature flag and the provider API key are configured, mirroring how the Google provider is registered; with either absent the send is a logged no-op and the email-dependent feature stays gated off, so Production is unchanged until a verified sender domain with SPF, DKIM, and DMARC and a key are in place. No token, link, or address is written to a log or the audit trail, which records the action, not the message. Bounce and complaint handling is deferred as out of scope for a single-school volume.

This design adds a provider dependency and sending-domain DNS setup, but it unblocks verified-email change, password recovery, and automatic invite delivery, keeps the provider replaceable behind one port, and stays fail-closed and test-driven so no email escapes an environment that is not deliberately configured to send.
